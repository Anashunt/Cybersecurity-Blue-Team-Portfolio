\# 🌩️ Tempest Incident — Malicious Document to Full System Compromise\## 🎯 Lab ObjectiveThis lab simulates a complete incident response investigation following the compromise of a Windows workstation through a malicious Microsoft Word document.The investigation focuses on reconstructing the attack chain by correlating \*\*endpoint telemetry, Windows Event Logs, Sysmon events, and network traffic\*\*. The objective is not limited to identifying the initial malicious document, but extends to tracing the attacker's activity through payload execution, command-and-control communication, internal reconnaissance, credential discovery, remote access, privilege escalation, and persistence.The investigation demonstrates how an Incident Responder can move from an initial high-severity alert to a complete understanding of the compromise by correlating artifacts across multiple data sources.\---\## 📌 Scenario OverviewA critical security alert indicated that a Windows workstation had been compromised through a malicious document.Initial triage established that:\* The malicious document used a `.doc` extension.\* The document was downloaded through `chrome.exe`.\* The document triggered a chain of child processes after execution.\* The resulting activity included encoded commands and remote payload retrieval.\* A second-stage binary established communication with attacker-controlled infrastructure.\* The attacker subsequently performed internal reconnaissance and credential discovery.\* A reverse SOCKS proxy was established to facilitate access to internal services.\* The attacker later obtained elevated privileges and established multiple persistence mechanisms.The investigation was therefore conducted as a timeline reconstruction rather than as an isolated malware-analysis exercise.\---\# 🛠️ Investigation Environment\## Data SourcesThe investigation relied primarily on three complementary data sources:\* \*\*Sysmon logs\*\* — process creation, file creation, network connections, and DNS queries\* \*\*Windows Event Logs\*\* — account creation and privilege-related activity\* \*\*Packet Capture (PCAP)\*\* — HTTP and C2 traffic analysis\## Tools Used\* \*\*EvtxECmd\*\* — Windows Event Log parsing\* \*\*Timeline Explorer\*\* — CSV-based event filtering and timeline analysis\* \*\*SysmonView\*\* — visual correlation of Sysmon events\* \*\*Event Viewer\*\* — Windows Event Log inspection and XML export\* \*\*Brim\*\* — rapid network-flow and HTTP investigation\* \*\*Wireshark\*\* — packet-level and HTTP stream analysis\* \*\*PowerShell\*\* — artifact hashing and command-line investigation\---\# 🔎 Investigation Walkthrough\## 1. Evidence Preparation and Integrity VerificationBefore beginning the investigation, the available artifacts were identified and their integrity was verified through SHA-256 hashing.The investigation files included:\* `capture.pcapng`\* `sysmon.evtx`\* `windows.evtx`PowerShell was used to navigate to the incident-artifact directory:```powershellcd '.\\\\Desktop\\\\Incident Files\\\\'```The available files were then reviewed:```powershellls```Each artifact was hashed using:```powershellGet-FileHash -Algorithm SHA256 .\\\\capture.pcapng```The same procedure was applied to the Sysmon and Windows Event Log files:```powershellGet-FileHash -Algorithm SHA256 .\\\\sysmon.evtxGet-FileHash -Algorithm SHA256 .\\\\windows.evtx```This provided a baseline for verifying that the supplied forensic artifacts remained unchanged during analysis.\---\# 2. Sysmon Log ParsingThe Sysmon Event Log contained the majority of the endpoint telemetry required for reconstructing the attack.Because raw EVTX data is difficult to investigate efficiently, \*\*EvtxECmd\*\* was used to convert the Sysmon log into CSV format.From the EvtxECmd directory, the following command was used:```powershell.\\\\EvtxECmd.exe -f 'C:\\\\Users\\\\user\\\\Desktop\\\\Incident Files\\\\sysmon.evtx' --csv 'C:\\\\Users\\\\user\\\\Desktop\\\\Incident Files' --csvf sysmon.csv```The resulting `sysmon.csv` file was then opened using \*\*Timeline Explorer\*\*:```textFile → Open → sysmon.csv```Timeline Explorer provided column-based filtering and global search functionality, allowing the investigation to isolate process names, command lines, PIDs, parent PIDs, hashes, network destinations, and other artifacts.\---\# 3. Sysmon Event IdentificationThe investigation focused primarily on several Sysmon Event IDs:| Event ID | Purpose                                      || -------: | -------------------------------------------- ||        1 | Process Creation                             ||        2 | File Creation Time Changed                   ||        3 | Network Connection                           ||        5 | Process Terminated                           ||        8 | CreateRemoteThread                           ||       11 | File Created                                 ||       12 | Registry Object Created/Deleted              ||       13 | Registry Value Set                           ||       15 | Alternate Data Stream / FileCreateStreamHash ||       22 | DNS Query                                    |Of particular importance were:\* \*\*Event ID 1\*\* for reconstructing the process tree\* \*\*Event ID 11\*\* for identifying dropped/created files\* \*\*Event ID 22\*\* for correlating malicious domains with endpoint activity\* \*\*Event ID 3\*\* for associating processes with outbound network connectionsThe investigation repeatedly correlated \*\*Process ID\*\* and \*\*Parent Process ID\*\* values to reconstruct the execution chain.\---\# 4. Initial Access — Malicious DocumentThe investigation began with the known initial-access vector: a malicious Microsoft Word document.Since the initial alert indicated that the document was downloaded through Chrome, process-creation events associated with `chrome.exe` were reviewed to identify the downloaded document.The resulting `.doc` filename was then correlated with subsequent \*\*WinWord.exe\*\* execution.The investigation confirmed that the document was opened by Microsoft Word and that its execution initiated a suspicious child-process chain.The compromised username and workstation name were identified by correlating the relevant Sysmon process events with the user and host fields.\---\# 5. Identifying the Microsoft Word ProcessThe next step was to determine which instance of `WinWord.exe` opened the malicious document.Sysmon \*\*Event ID 1\*\* records were filtered for Microsoft Word executions:```textImage contains WinWord.exe```The relevant event was then correlated using:```textProcess IDParent Process IDCommand LineUserComputer```This allowed the investigation to identify the exact Word process associated with the malicious document rather than unrelated Word activity.The PID of the compromised Word process was subsequently used as an anchor for identifying its child processes.\---\# 6. Malicious Domain ResolutionAfter establishing the malicious document's execution chain, the investigation moved to DNS activity.Sysmon \*\*Event ID 22 — DNS Query\*\* was reviewed for domains generated by the malicious document.The relevant domain was correlated with the IPv4 address returned by the DNS resolution.This created an important relationship:```textMalicious Document\&#x20;       ↓WinWord.exe\&#x20;       ↓Malicious Domain\&#x20;       ↓Resolved IPv4 Address```This endpoint-side evidence was later correlated with the packet capture to confirm the same infrastructure from the network perspective.\---\# 7. Encoded Command ExecutionThe process tree revealed that Microsoft Word spawned a suspicious command interpreter/process.The corresponding \*\*Event ID 1\*\* record was inspected, with particular attention given to the `CommandLine` field.The command contained a Base64-encoded component.The encoded value was isolated from the command line and decoded to reconstruct the actual command chain executed by the malicious document.This established that the document was not simply opening an embedded file; it was actively executing an encoded command to continue the infection.The decoded command was then used as a pivot for identifying the next stage of execution.\---\# 8. Exploit IdentificationThe process chain and malicious document behavior were correlated with the known exploitation technique used to achieve code execution.The investigation compared the observed execution behavior with the exploit artifacts recorded in the Sysmon telemetry, allowing the corresponding \*\*CVE\*\* to be identified.This provided the final link between the malicious document and the remote-code-execution stage.\---\# 9. Stage 2 Payload IdentificationAfter decoding the initial command, the investigation revealed that the malicious execution wrote a second-stage payload onto the workstation.Sysmon \*\*Event ID 11 — File Created\*\* was used to identify newly created files immediately following the document execution.Timeline Explorer was searched around the execution timeframe for:```textEvent ID = 11```and correlated against:```textParentProcessIDProcessIDImageTargetFilename```This identified the complete filesystem path used for the stage 2 payload.\---\# 10. Persistence Through User LogonThe investigation then examined activity associated with `explorer.exe`, because the available telemetry indicated that the implanted payload executed when the compromised user logged into the workstation.The process tree was reconstructed by following:```textexplorer.exe\&#x20;   ↓child process\&#x20;   ↓malicious payload```The corresponding command line revealed the command executed after successful user logon.This established that the attacker had already introduced an \*\*autostart mechanism\*\* before continuing with the remaining stages of the attack.\---\# 11. Stage 2 Binary Hash IdentificationThe malicious stage 2 binary was identified through the corresponding Sysmon process and file-creation events.Its SHA-256 hash was extracted from the telemetry and used as a unique identifier for the binary.This allowed the endpoint artifact to be tracked independently of its filename or filesystem location.The hash was subsequently used to identify the binary's role within the wider attack chain.\---\# 12. Network Traffic InvestigationOnce the malicious domains and stage 2 infrastructure had been identified from Sysmon, the packet capture was introduced into the investigation.Two complementary tools were used:\* \*\*Brim\*\* for rapid traffic discovery and correlation\* \*\*Wireshark\*\* for packet-level inspection and HTTP stream reconstructionBrim was used to locate HTTP traffic associated with the known malicious infrastructure.A targeted Brim filter was used in the investigation:```text\\\_path=="http" "<malicious domain>"```For chronological HTTP analysis, the following type of query was used:```text\\\_path=="http" "<malicious domain>" id.resp\\\_p==<C2 port>| cut ts, host, id.resp\\\_p, uri| sort ts```This allowed the HTTP requests to be ordered chronologically and correlated with the endpoint events.\---\# 13. Malicious Payload DeliveryThe packet capture was searched for the URL used by the malicious document to retrieve its payload.The HTTP request was then opened in Wireshark to inspect:\* HTTP method\* Host header\* Request URI\* User-Agent\* Response headers\* Payload transferThe malicious URL identified in the document was correlated with the same network activity observed in the PCAP.This confirmed that the document's execution resulted in an actual remote payload retrieval rather than an isolated local execution.\---\# 14. C2 Traffic AnalysisThe stage 2 binary subsequently established communication with attacker-controlled infrastructure.Brim was used to isolate HTTP requests associated with the C2 domain and port.The requests were inspected for:\* HTTP method\* URI\* Parameters\* Encoded data\* Server responses\* Repeated communication patternsThe traffic revealed an encoded communication mechanism between the compromised host and the attacker-controlled server.The encoding format was identified by examining the transmitted data and comparing its structure across multiple requests.\---\# 15. Command-and-Control Request StructureThe C2 binary did not simply establish a connection and remain idle. It repeatedly contacted specific URLs to retrieve commands and submit command output.The HTTP requests were reconstructed using Wireshark's:```textFollow → HTTP Stream```The stream analysis exposed the request structure and the parameter used to transport command results.The corresponding URL used to retrieve commands was also identified.This allowed the investigation to reconstruct the C2 communication model:```textVictim\&#x20; ↓HTTP Request\&#x20; ↓C2 Server\&#x20; ↓Command\&#x20; ↓Victim Execution\&#x20; ↓Encoded Command Output\&#x20; ↓C2 Server```\---\# 16. User-Agent and Programming Language AttributionThe HTTP `User-Agent` associated with the malicious C2 traffic was inspected.Wireshark was used to expose the HTTP request headers, specifically:```texthttp.user\\\_agent```The unusual User-Agent provided an additional artifact that could be used for malware identification and detection engineering.The User-Agent characteristics also allowed the programming language used to compile the malicious binary to be inferred.\---\# 17. Internal ReconnaissanceOnce the C2 communication pattern had been established, the investigation moved from infrastructure identification to attacker activity.The HTTP traffic was filtered to identify requests containing encoded command data.The encoded C2 payloads were decoded to reveal the commands executed on the compromised workstation.The commands showed that the attacker was performing internal reconnaissance rather than simply maintaining a beacon.Particular attention was given to commands related to:\* Host information\* Network configuration\* Listening ports\* Local users\* Files\* Credentials\* ServicesThis established that the attacker had moved into the \*\*Discovery\*\* phase of the intrusion.\---\# 18. Credential DiscoveryThe attacker subsequently accessed a sensitive file on the compromised workstation.The file contents revealed credentials that could be used for further access.The discovered credentials were correlated with the subsequent network and process activity to determine how they were used.This represented a major escalation in the attack because the attacker now possessed credentials that could potentially provide access to internal services beyond the initially compromised workstation.\---\# 19. Listening-Port EnumerationThe attacker enumerated listening ports on the compromised machine.The resulting command output revealed a service capable of providing remote shell access.The port was correlated against subsequent network activity to determine whether the attacker later used the discovered service.This demonstrated how the attacker used host-level reconnaissance to identify additional avenues for remote access.\---\# 20. Reverse SOCKS ProxyThe attacker then established a reverse SOCKS proxy from the compromised workstation.The malicious command responsible for establishing the proxy was identified by correlating the C2 traffic with the corresponding Sysmon \*\*Event ID 1\*\* process creation event.The exact command line was recovered from the `CommandLine` field.The binary used for the SOCKS proxy was identified through its process execution and SHA-256 hash.The hash was then used to identify the underlying tool.This stage was particularly significant because the proxy allowed the attacker to use the compromised workstation as a pivot point into internal services that were not directly exposed to the attacker.\---\# 21. Remote AuthenticationAfter establishing the reverse SOCKS proxy, the attacker used the previously harvested credentials to authenticate to another service.The process executed immediately after the proxy activity was examined to determine the protocol/service used for authentication.Endpoint process telemetry and network traffic were correlated to establish the relationship:```textCredential Discovery\&#x20;       ↓Reverse SOCKS Proxy\&#x20;       ↓Remote Authentication\&#x20;       ↓Internal Access```This marked the transition from a single-host compromise to an internal-access and lateral-movement phase.\---\# 22. Privilege EscalationAfter obtaining stable access, the attacker investigated the privileges available to the compromised user.The process tree and C2 traffic were examined for commands that queried or manipulated the user's privileges.The attacker subsequently downloaded another binary specifically intended for privilege escalation.The binary was identified through its:\* Filename\* SHA-256 hash\* Execution context\* Parent process\* Network sourceThe hash was then correlated with threat-intelligence information to identify the privilege-escalation tool.\---\# 23. Exploiting a High-Privilege User TokenThe privilege-escalation tool was used to exploit a specific privilege assigned to the compromised account.The relevant privilege was identified from the command execution and surrounding telemetry.The attacker then used the privilege-escalation tool together with another binary to establish a new C2 connection under an elevated security context.The resulting process tree demonstrated that the attacker had successfully moved from the original user context toward \*\*SYSTEM-level execution\*\*.The second C2 connection was also observed using a different destination port from the original C2 channel.\---\# 24. SYSTEM-Level ActivityFollowing successful privilege escalation, the attacker operated under:```textNT AUTHORITY\\\\SYSTEM```This provided significantly greater control over the workstation.The investigation therefore shifted its focus to child processes spawned by the newly elevated malicious C2 binary.Brim was again used to identify HTTP activity associated with the elevated C2 channel:```text\\\_path=="http" "<malicious domain>" id.resp\\\_p==<C2 port>| cut ts, host, id.resp\\\_p, uri| sort ts```The resulting activity was correlated with Sysmon and Windows Event Logs to identify actions performed after SYSTEM access was obtained.\---\# 25. Creation of Additional AccountsAfter obtaining SYSTEM privileges, the attacker created two local accounts.The account-creation commands were identified through Sysmon process creation events.The investigation also revealed earlier failed account-creation attempts.The failed commands were compared against the successful execution to identify the missing command-line option that caused the initial attempts to fail.\---\# 26. Windows Event Log CorrelationThe successful account creation was independently validated through Windows Event Logs.The account-creation event was identified and correlated with the corresponding process execution.This provided two independent sources of evidence:```textSysmon\&#x20; ↓Command executed to create account\&#x20; ↓Windows Event Log\&#x20; ↓Successful account creation```This type of correlation strengthened the finding because the account creation was not inferred solely from process execution; it was confirmed by Windows' own security auditing.\---\# 27. Local Administrator Group ModificationOne of the newly created accounts was subsequently added to the local Administrators group.The relevant command was identified through the process-creation telemetry.The corresponding Windows Event Log entry was then used to validate that the account had successfully been added to the sensitive local group.This established that the attacker had created an administrative backdoor rather than merely creating dormant accounts.\---\# 28. Persistence EstablishmentFollowing account creation and privilege escalation, the attacker executed another persistence technique designed to maintain administrative access.The command responsible for establishing the persistence mechanism was recovered directly from the relevant process-creation event.The investigation correlated:\* Process creation\* User context\* Command line\* Windows Event Logs\* Parent/child process relationshipsto establish the complete persistence sequence.At this stage, the attacker had multiple mechanisms capable of maintaining access even if the original execution chain was interrupted.\---\# 🧩 Attack Chain ReconstructionThe investigation ultimately reconstructed the following provides the complete story\*\*.The initial malicious-document alert represented only the beginning of the incident. By following process ancestry, DNS activity, file creation, network connections, HTTP streams, and Windows security events, the investigation expanded from a single suspicious document into a complete compromise timeline.The strongest findings were produced by \*\*correlating independent evidence sources\*\* rather than relying on a single artifact.The final investigation therefore progressed through:```textAlert\&#x20; ↓Initial Access\&#x20; ↓Execution\&#x20; ↓Payload Retrieval\&#x20; ↓C2\&#x20; ↓Reconnaissance\&#x20; ↓Credential Discovery\&#x20; ↓Lateral Access\&#x20; ↓Privilege Escalation\&#x20; ↓SYSTEM\&#x20; ↓Persistence```This workflow reflects a practical Tier 1/Tier 2 SOC investigation methodology for reconstructing a multi-stage Windows intrusion from endpoint and network telemetry.
