\# 🐞 ItsyBitsy — C2 Communication Investigation (Tier 1 SOC)\## 🎯 Lab ObjectiveThis lab simulates a Tier 1 SOC investigation into a potential Command-and-Control (C2) communication detected by an IDS.The objective was to investigate network connection logs associated with a potentially compromised user, identify the suspicious external infrastructure involved in the communication, trace the file accessed from that infrastructure, and recover the malicious artifact associated with the incident.The investigation was performed using HTTP connection logs ingested into Kibana, demonstrating how a SOC analyst can investigate a network-based alert even when full endpoint telemetry is unavailable.\## 📌 Scenario OverviewDuring routine SOC monitoring, an IDS generated an alert indicating potential C2 communication originating from a workstation associated with an HR user.Because endpoint telemetry was limited, the investigation relied primarily on a week of HTTP connection logs stored in the `connection\\\_logs` index within Kibana.The investigation followed the network activity of the suspected host to:1\. Identify the workstation associated with the suspicious user.2\. Establish the normal and anomalous HTTP communication patterns observed from the host.3\. Identify the legitimate Windows binary involved in downloading external content.4\. Investigate connections to a legitimate file-sharing service that was also being abused as part of the malware's C2 infrastructure.5\. Identify the specific C2 URL contacted by the compromised host.6\. Trace the file accessed through the C2 infrastructure.7\. Extract the malicious pattern contained within the retrieved file.This approach demonstrates how seemingly legitimate web services and binaries can be abused by malware and why C2 investigations require correlation between user activity, destination infrastructure, URLs, and accessed resources.\## 🛠️ Tools Used\* \*\*Kibana / Elastic Stack\*\* — SIEM investigation and HTTP connection-log analysis\* \*\*KQL\*\* — Filtering and narrowing network events\* \*\*HTTP connection logs\*\* — Source of network-level investigation data\* \*\*Threat intelligence / infrastructure analysis\*\* — Identification and validation of suspicious external services\## 🔍 Analysis Walkthrough\### 1. Establishing the Investigation ScopeThe investigation began by querying the `connection\\\_logs` index in Kibana and determining the volume of events available for the relevant investigation period.Rather than reviewing the complete dataset manually, the logs were progressively filtered to isolate the activity associated with the suspected HR workstation.This established the baseline dataset from which the remaining investigation was conducted.\### 2. Identifying the Suspected HostThe logs were filtered around the activity associated with the suspected user to determine which internal IP address was responsible for the observed connections.Once the associated source address was identified, it was used as the primary pivot for the remainder of the investigation.This allowed the investigation to move from a user-based alert to a network-based investigation centered around a specific workstation.\### 3. Investigating Download ActivityThe HTTP logs were then reviewed for outbound requests generated by the identified workstation.Particular attention was given to requests involving file downloads and unusual external destinations.The investigation revealed that the workstation used a legitimate Windows system binary to retrieve an external file. Although the binary itself was legitimate, its use for downloading content from an external C2 infrastructure represented suspicious behavior and provided an important behavioral indicator.\### 4. Identifying the Abused File-Sharing InfrastructureFurther correlation of the workstation's HTTP connections revealed communication with a well-known legitimate file-sharing service.The service itself was not inherently malicious; however, its presence in the communication chain was significant because the infrastructure was being used by the malware authors to facilitate C2 communication.This highlighted an important SOC detection concept: \*\*malicious activity does not necessarily communicate exclusively with infrastructure that is inherently malicious.\*\*Legitimate services can be abused as part of malware delivery and command-and-control operations, making contextual analysis of HTTP activity essential.\### 5. Tracing the C2 CommunicationThe HTTP requests associated with the suspicious external service were examined to identify the exact resource being contacted by the compromised workstation.By correlating the source host, destination service, requested URI, and surrounding HTTP events, the investigation isolated the C2 endpoint responsible for the suspicious communication.The identified URL was then treated as a key IOC for the investigation.\### 6. Investigating the Accessed FileAfter identifying the C2 endpoint, the associated HTTP activity was examined to determine which remote file was accessed by the compromised host.The requested filename provided an additional artifact that could be used to correlate the network activity with the malicious operation.The file was then treated as part of the C2 communication chain rather than as an isolated download.\### 7. Extracting the Malicious ArtifactThe contents associated with the accessed file were reviewed to identify the embedded malicious pattern.The investigation ultimately recovered a value matching the expected `THM{...}` pattern, confirming that the previously identified network activity was directly associated with the malicious artifact referenced by the IDS alert.\## 🧩 Investigation FlowThe investigation followed a progressive pivoting methodology:\*\*IDS Alert\*\*→ \*\*Suspected User\*\*→ \*\*Internal Host / Source IP\*\*→ \*\*HTTP Activity\*\*→ \*\*Download Behavior\*\*→ \*\*Legitimate Windows Binary\*\*→ \*\*Abused File-Sharing Infrastructure\*\*→ \*\*C2 URL\*\*→ \*\*Accessed File\*\*→ \*\*Malicious Artifact\*\*This progression demonstrates how a SOC analyst can reconstruct an incident from limited network telemetry by continuously pivoting from one observable artifact to another.\## ✅ Summary of
